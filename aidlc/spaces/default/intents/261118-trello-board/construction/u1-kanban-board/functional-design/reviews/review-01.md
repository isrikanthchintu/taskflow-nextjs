| R-01 | Major | `construction/u1-kanban-board/functional-design/functional-spec.md` > W6 step 3, and `frontend-components.md` > KanbanColumn section | The documents state the column's live count is "the filtered, not total, count per FR1.2," but FR1.2 in `requirements.md` says the header count should reuse "the existing per-status counts already computed today (`counts.todo`, `counts.active`, `counts.done`)". In the current codebase (`src/components/task-dashboard.tsx`), `counts` is computed from the full, unfiltered `tasks` array (not `filteredTasks`) — it is the total per-status count shown in today's stat cards and filter tabs, unaffected by the search box. The design therefore cites FR1.2 as justification for a behavior (filtered count) that the actual wording and the existing reused computation point the opposite way (total, unfiltered count). This is a real ambiguity the design should resolve explicitly rather than assert as if settled, since it changes what a developer implements for `KanbanColumn`'s header. | Either correct the citation (if filtered count is the intended product behavior, state it as a deliberate UX decision rather than attributing it to FR1.2, which says the opposite), or change the design to show the total per-status count matching `counts.todo`/`counts.active`/`counts.done` as FR1.2 literally directs, and update `KanbanColumn`'s prop/count derivation accordingly in both `functional-spec.md` and `frontend-components.md`. | New |
| R-02 | Major | `construction/u1-kanban-board/functional-design/functional-spec.md` (W2, W3, W5) and `frontend-components.md` (Props/State per Component, throughout) | The stage definition's Step 4 requires these artifacts to be "Technology-agnostic — implementable in any language. No code, no SQL, no framework references," limiting code to short illustrative snippets. Both documents go well beyond naming the already-decided library (ADR-002 names `@dnd-kit/core`/`@dnd-kit/sortable`) and repeatedly specify concrete, versioned API surface — `DndContext`, `PointerSensor`, `KeyboardSensor`, `SortableContext`, `useSortable`, `onDragEnd` — as if these interface names were already fixed design decisions. This crosses from behavioral/interaction design into framework-specific implementation detail that belongs in Code Generation, and risks locking in API choices (e.g., exactly which sensor types, exactly which hook) that Code Generation should still be free to verify against the installed package version. | Rewrite the drag/keyboard interaction descriptions in library-agnostic terms (e.g., "a pointer- and keyboard-operable drag session," "an ordered-list container exposing drop targets") and move the specific API names (`DndContext`, `KeyboardSensor`, `useSortable`, etc.) out of the design narrative, reserving them for Code Generation where implementation specifics belong. | New |
| R-03 | Minor | `construction/u1-kanban-board/functional-design/functional-spec.md` > W2 step 1 | W2 asserts that `@dnd-kit`'s `KeyboardSensor` alone provides the keyboard-operable equivalent for cross-column drag (Arrow keys moving a card between different columns), presented as already working from adopting the library (ADR-002). In practice, `@dnd-kit`'s default keyboard sortable coordinate logic only reorders within a single sortable container; moving an item between separate column containers via arrow keys typically needs a custom coordinate-getter that is not mentioned anywhere in the design. This doesn't block NFR3, since W4's dedicated non-drag control already provides a working keyboard equivalent for column changes, but the claim in W2 could mislead whoever implements it into assuming cross-column keyboard-drag works out of the box. | Either qualify W2 step 1 to say the keyboard-driven column change is provided via the separate control in W4 (not via arrow-key cross-column dragging), or explicitly flag that cross-column keyboard dragging would require additional custom wiring if it is actually intended to work that way. | New |
